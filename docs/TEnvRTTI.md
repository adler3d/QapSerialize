# QapFramework: История одной архитектурной одержимости

## Вместо вступления

Когда я начинал этот проект в 2008 году, я даже не подозревал, что строю не просто библиотеку, а **экосистему**, которая переживёт все мои представления о том, каким должен быть C++.

Это не статья про "очередной фреймворк". Это история о том, как одна идея — *"а что если объекты сами знают, как себя сохранять?"* — превратилась в монолитную платформу, из которой нельзя ничего выкинуть, не разрушив всё здание.

---

## Часть 1. Истоки: Delphi-мышление в C++

### 1.1. Стиль разработки

Всё началось с Delphi 7. Там был простой принцип: **всё состояние программы — в одном файле**. Положил компонент на форму, настроил в Object Inspector, сохранил — и готово. Никаких скриптов, никаких ручных связей.

Когда я перешёл на C++, этот стиль остался со мной. Но в C++ нет Object Inspector. И я решил: *"А сделаю-ка я свой"*.

### 1.2. Первая идея

В 2008 году я написал:

```cpp
class TNode {
    TSelfPtr<TNode> Self;  // Что это? Пока не знаю
    string Name;
    int Value;
};
```

Я хотел, чтобы этот класс:
1. Автоматически сериализовался
2. Знать структуру в рантайме
3. Безопасно ссылаться на другие объекты
4. Переживать перемещение в памяти

Тогда я не знал, что это будет стоить мне 5 лет жизни.

## Часть 2. Архитектура: как всё устроено на самом деле

### 2.1. Ядро: TServerPtrSpace

Это **глобальное пространство имён** для всех объектов системы. Но есть важный нюанс: оно живёт **только во время сериализации**:

```cpp
class TEnvRTTI {
    // При сохранении/загрузке создаётся временное пространство
    TServerPtrSpace Space;  // Живёт только в методах Save/Load!
};
```

В режиме нормальной работы пространство **не нужно**. Более того, его создание в рантайме замедляет всё. Поэтому в `TEnvRTTI` оно существует, но активно только во время сериализации.

#### Что хранится в TServerPtrSpace:

```cpp
struct EnvItem {
    EnvVoidPtr ptr;        // Указатель на объект
    EnvVoidPtr ptr_lnk;    // Ссылка на парный объект
    string name;           // Имя для отладки
    bool system;           // Системный объект
    int count;             // Счётчик использований
    bool passed;           // Флаг обхода
    int id;                // SaveID (временный!)
};
```

**SaveID** — это временный идентификатор, который существует только во время сериализации. Его можно использовать для своих целей, если не страшно, что он перезапишется.

### 2.2. Умные указатели: не то, чем кажутся

В отличие от `std::shared_ptr`, мои указатели **не управляют временем жизни**:

```cpp
// TSelfPtr — встроенный сервер ссылок
class TSelfPtr<T> {
    TServerPtr<T> P;  // Содержит список клиентов
    int SaveID;       // Только для сериализации!
};

// TWeakPtr — автоматически инвалидируется
class TWeakPtr<T> {
    TServerPtr<T>* P;  // nullptr при удалении объекта
};

// THardPtr — не владеющий счётчик
class THardPtr<T> {
    TServerPtr<T>* P;  // Увеличивает HardCount
    // HardCount == 1 > можно удалить
};

// TAutoPtr — владеющий указатель
class TAutoPtr<T> {
    TRTTIProduct Product;  // Содержит тип и память
};
```

**Ключевое отличие:** объекты удаляются **явно**, а не по счётчику. `THardPtr` просто считает ссылки, чтобы ты знал, что объект никто не держит.

### 2.3. Два мира: TType и DeclareType

Это самое важное архитектурное решение.

**Исполнительный мир (TType):**
- Реальные указатели на объекты
- Вычисленные оффсеты полей
- Фабрики и аллокаторы
- Используется в рантайме

**Декларативный мир (DeclareType):**
- Только имена и структура
- Слабые ссылки на другие типы
- Нет оффсетов (пересчитываются при загрузке)
- Используется для сериализации

Конвертация между мирами — это `TMegaSolver`:

```cpp
// TType > DeclareType (для сохранения)
void DoConv(DeclareTypeStruct* out, TTypeStruct* in) {
    out->Name = in->Info.Name;        // Только имя!
    // Оффсеты НЕ сохраняются
}

// DeclareType > TType (для загрузки)
void DoConv(TTypeStruct* out, DeclareTypeStruct* in) {
    out->Info.Name = in->Name;
    out->Info.Align = -1;  // Будет пересчитан
    out->Info.Size = -1;   // Будет пересчитан
    // После загрузки > ReCalcMembersOffset()
}
```

### 2.4. Миграция данных: LastHope

Это то, что делает систему живой:

```cpp
class TBinaryLoaderLastHope {
    void LoadOldObjectAndConvertToNewFormat(
        TTypeStruct* new_version,      // Новая структура
        DeclareTypeStruct* old_version // Старая структура
    ) {
        // Поля, которые есть в старой версии > загружаем
        // Поля, которых нет > игнорируем
        // Новые поля > получают значения по умолчанию
        
        for (auto& old_field : old_version->Members) {
            auto* new_field = new_version->find_member(old_field.Name);
            if (!new_field) continue;  // Поле удалено
            LoadField(new_field, old_field);
        }
    }
};
```

**Что это даёт:**
- ? Можно добавлять новые поля
- ? Можно удалять старые поля
- ? Можно менять порядок полей
- ? Нельзя менять тип поля (нужен конвертер)

## Часть 3. Инструменты: QapTreeDebugger и BranchLexem

### 3.1. QapTreeDebugger

Это визуальный инспектор объектов. Он позволяет:
- Обходить граф объектов в рантайме
- Редактировать поля (числа, строки, цвета)
- Работать с умными указателями
- Управлять векторами (добавлять/удалять элементы)

**Горячие клавиши (было их много):**
- `F10` — захватить объект под мышкой
- `Ctrl+Click` — редактировать поле
- `Ctrl+Shift` — инкремент/декремент чисел
- `Delete` — обнулить/удалить
- `+/-` на векторе — добавить/удалить элемент

**Почему это fail:** слишком сложно для повседневного использования. Требует запоминания кучи горячих клавиш. Неудобно для массовых изменений.

### 3.2. BranchLexem

Это **скриптовый язык** для настройки объектов:

```cpp
// Вместо кликов в QapTreeDebugger:
auto game = root.game;
game.You = player;
game.Bots.emplace_back();
game.Bots[0] = bot1;
game.Bots[0].hp = 100;
```

**Что даёт:**
- ? Автодополнение (как в IDE)
- ? Сохранение скриптов
- ? Переиспользование
- ? Массовые изменения
- ? Контроль версий

**Что ограничивает:**
- ? Нет условий и циклов
- ? Нет арифметики
- ? Только чтение/запись полей

## Часть 4. Почему это работает

### 4.1. Game Loop вместо событий

Вся система построена на **Game Loop**:

```cpp
while (running) {
    ProcessInput();  // Опрос клавиатуры/мыши
    Update();        // 64 тика в секунду
    Render();        // Отрисовка
}
```

Это позволяет:
- Сохранять состояние в любой момент
- Иметь полный контроль над порядком обновления
- Просто отлаживать (всё в одном месте)

Альтернатива — событийная модель — не подходит, потому что:
- Сложно синхронизировать
- Трудно сохранять состояние
- Непредсказуемый порядок

### 4.2. Всё через RTTI

Каждый объект знает свою структуру:

```cpp
// Можно обойти все поля:
auto* type = obj->GetMetaType(env);
for (auto& member : type->Members) {
    void* value = member.getValue(obj);
    // Работаем с полем
}
```

Это позволяет:
- Автоматическая сериализация
- Миграция данных
- QapTreeDebugger
- BranchLexem

### 4.3. Состояние как файл

Стиль, который пришёл из Delphi:

```cpp
// Всё состояние — в одном файле
LoadState("program.bin");  // Загрузили
// ... работаем ...
SaveState("program.bin");  // Сохранили

// Настройка — один раз
// Сохранили > закоммитили > готово!
```

## Часть 5. Что я понял за эти годы

### 5.1. Монолитность — это ловушка

Когда система становится монолитной, ты не можешь:
- Убрать устаревшие фичи
- Заменить части на более современные
- Экспериментировать с альтернативами

Каждый компонент необходим для работы других:

| Компонент | Без него не работают |
|-----------|---------------------|
| TServerPtrSpace | Умные указатели, сериализация, миграция |
| TSelfPtr | Умные указатели, перемещение |
| TWeakPtr | Безопасные ссылки |
| THardPtr | Контроль удаления |
| TType | RTTI, сериализация |
| DeclareType | Сериализация, миграция |
| TMegaSolver | Миграция данных |
| SaveID | Сериализация, миграция |

**Ничего нельзя выкинуть.**

### 5.2. Синергия — это обоюдоострый меч

Синергия фич:
- ? **Хорошо:** когда они усиливают друг друга
- ? **Плохо:** когда становятся неразрывно связанными

Пример:

```cpp
// TServerPtrSpace + TSelfPtr + TWeakPtr = безопасные ссылки
// + TType = RTTI
// + DeclareType = сериализация
// + TMegaSolver = миграция
// + SaveID = глобальная идентификация

// Всё это работает вместе
// Но нельзя заменить одну часть
```

### 5.3. Иллюзия "бесплатной" функциональности

Когда система обещает, что "всё будет автоматически", она:
- Скрывает сложность
- Создаёт ложное чувство безопасности
- Наказывает при попытке выйти за рамки

**Пример:**

```cpp
// Ты просто добавляешь поле:
struct t_node {
    int x;
    int y;
    string name;  // Новое поле!
};

// Система автоматически:
// 1. Обновляет TType
// 2. Обновляет DeclareType
// 3. Обновляет сериализацию
// 4. Добавляет миграцию

// Но если ты хочешь изменить тип поля — нужно писать конвертер!
// А если хочешь удалить поле — данные теряются!
```

## Часть 6. Цена вопроса

### 6.1. Что я получил

1. **Мощную систему управления объектами**
   - Автоматическая инвалидация ссылок
   - Перемещение в памяти
   - Безопасное удаление

2. **Полноценную RTTI**
   - Интроспекция типов
   - Обход полей
   - Создание объектов по типу

3. **Сериализацию с миграцией**
   - Сохранение/загрузка любого графа
   - Конвертация между версиями
   - Единый формат хранения

4. **Инструменты для отладки**
   - QapTreeDebugger
   - BranchLexem

### 6.2. Что я потерял

1. **Гибкость**
   - Нельзя просто добавить поле
   - Нельзя использовать стандартные инструменты
   - Всё завязано на систему

2. **Время компиляции**
   - 7000+ строк парсера
   - Миллиарды инстанцирований шаблонов
   - 15-30 минут сборки

3. **Переносимость**
   - Завязан на MSVC
   - Использует особенности компилятора
   - Сложно портировать на другие платформы

4. **Простоту**
   - Новичку невозможно понять
   - Даже автор забывает, как что работает
   - Документация не спасает

## Часть 7. Где это живёт сейчас

### 7.1. Две системы в одном фреймворке

На самом деле у меня есть **две системы**:

**1. Тяжёлая RTTI-система** (то, о чём статья)
- TEnvRTTI
- TSelfPtr, TWeakPtr, THardPtr
- TType, DeclareType
- TMegaSolver
- QapTreeDebugger, BranchLexem

**2. Лёгкая система сериализации** (скрытый герой)
```cpp
// defprovar.inl — простые макросы для описания структур
#define DEF_PRO_VARIABLE(ADDBEG,ADDVAR,ADDEND) \
    ADDBEG() \
    ADDVAR(0,vector<EnvType>,Arr,DEF,$,$) \
    ADDEND()

// =====+>>>>>TEnvRTTI
#include "QapGenStruct.inl"
// <<<<<+=====TEnvRTTI
```

Она:
- Компилируется мгновенно
- Не требует RTTI
- Работает на любом компиляторе
- Простая и надёжная

Я использую её для 95% задач. Тяжёлая система — только для особых случаев.

### 7.2. Почему я не переписал всё заново

Потому что это **работает**. Система проверена годами. Она решает задачи, которые не решает ни одна другая система в мире C++.

Но она **слишком сложна** для 2024 года.

## Часть 8. Уроки

### 8.1. Архитектура — это искусство принимать решения, которые потом будет трудно отменить

Каждое решение в этой системе было правильным в момент принятия. Но вместе они создали монолит, из которого нельзя ничего выкинуть.

### 8.2. Инструменты должны быть простыми

QapTreeDebugger был слишком сложным. BranchLexem — слишком простым. Нужно было найти золотую середину.

### 8.3. Время компиляции — это ресурс

Когда проект перестаёт компилироваться за разумное время, ты перестаёшь его развивать. 15-30 минут сборки — это убийца продуктивности.

### 8.4. Нет бесплатных обедов

Система обещала: "Всё будет просто, всё будет автоматически". Она сдержала обещания... но не предупредила о цене.

# Документация к системе следящих указателей

## Проблема

В большинстве программ объекты постоянно ссылаются друг на друга.

Например:

```cpp
class Node
{
public:
  Node* Parent;
  std::vector<Node*> Children;
};
```

Такой код работает до тех пор, пока кто-нибудь не удалит объект.

После удаления все указатели на него превращаются в висячие ссылки.

```cpp
delete node;
```

После этого любой код вида

```cpp
node->Parent
```

или

```cpp
children[i]
```

может обратиться к уже освобождённой памяти.

Обычно проблему решают несколькими способами:

* ручным обнулением ссылок;
* использованием `shared_ptr` и `weak_ptr`;
* централизованным управлением объектами через контейнеры и идентификаторы.

У каждого подхода есть свои недостатки.

Ручное обнуление легко забыть.

`shared_ptr` требует специальной модели владения объектами.

Идентификаторы усложняют доступ к данным и требуют постоянных поисков объектов по таблицам.

В этой библиотеке используется другой подход.

Каждый объект самостоятельно знает, кто на него ссылается.

Когда объект уничтожается, все зарегистрированные ссылки автоматически получают значение `nullptr`.

---

## Основная идея

Каждый объект содержит специальный сервер ссылок.

Схематично это выглядит так:

```text
      TWeakPtr
          |
          v

+------------------+
|      Object      |
|                  |
|  TSelfPtr Self   |
+------------------+

          ^
          |
      TWeakPtr
```

Все слабые ссылки регистрируются внутри объекта.

Объект не знает, кто именно его использует.

Он знает только список клиентов.

При уничтожении объекта сервер проходит по списку клиентов и отключает их.

После этого все ссылки автоматически становятся пустыми.

---

## TSelfPtr

`TSelfPtr<T>` является встроенным сервером ссылок объекта.

Обычно он объявляется первым полем класса:

```cpp
class t_node
{
public:
  TSelfPtr<t_node> Self;

  bool enabled;
  vec2d pos;
};
```

Внутри `TSelfPtr` находится объект:

```cpp
TServerPtr<T>
```

который хранит список всех подключённых клиентов.

Сам объект обычно не использует `Self` напрямую.

Поле существует главным образом для обслуживания внешних ссылок.

---

## TWeakPtr

`TWeakPtr<T>` представляет собой автоматически отслеживаемую ссылку.

Пример:

```cpp
TWeakPtr<t_node> SelectedNode;
```

Назначение выполняется обычным образом:

```cpp
SelectedNode = &node;
```

После присваивания ссылка регистрируется внутри `node.Self`.

Если объект будет уничтожен, ссылка автоматически станет пустой.

Проверка выглядит привычно:

```cpp
if (SelectedNode)
{
  SelectedNode->pos.x += 10;
}
```

Получение объекта:

```cpp
auto* ptr = SelectedNode.get();
```

Если объект уже уничтожен, будет возвращён `nullptr`.

---

## Что происходит при удалении объекта

Пусть существует объект:

```cpp
t_node node;
```

и несколько ссылок:

```cpp
TWeakPtr<t_node> A;
TWeakPtr<t_node> B;
TWeakPtr<t_node> C;

A = &node;
B = &node;
C = &node;
```

Внутри объекта образуется список клиентов:

```text
node
 |
 +-- A
 |
 +-- B
 |
 +-- C
```

Во время уничтожения объекта вызывается отключение всех клиентов.

После завершения операции получаем:

```cpp
A == nullptr
B == nullptr
C == nullptr
```

Никаких висячих указателей не остаётся.

---

## Для чего система создавалась

Первоначальная цель системы состояла не в замене `shared_ptr`.

Основная задача была другой.

Необходимо было безопасно хранить ссылки между объектами большого графа данных:

* узлами;
* связями;
* элементами редактора;
* объектами RTTI-системы.

При этом требовалось:

* быстро получать объект по указателю;
* не использовать глобальные таблицы;
* автоматически инвалидировать ссылки после удаления объекта.

Именно под эти требования была построена модель с `TSelfPtr`, `TServerPtr` и `TWeakPtr`.

# Внутреннее устройство системы

## TServerPtr

Центральным элементом системы является:

```cpp
TServerPtr<T>
```

Именно он хранит информацию обо всех подключённых клиентах.

Упрощённо его состояние можно представить так:

```cpp
template<class T>
class TServerPtr
{
public:
  T* ptr;

  int RefCount;
  int HardCount;

  TClientPtr<T> entry_point;
  THardClientPtr<T> hard_point;
};
```

Каждый объект содержит один экземпляр `TServerPtr`, расположенный внутри поля `TSelfPtr`.

---

## Почему используются списки клиентов

Большинство реализаций слабых ссылок используют отдельный управляющий блок.

В данной системе управляющий блок находится внутри самого объекта.

Поэтому объект всегда знает, кто на него ссылается.

Схематично:

```text
       Object

      +------+
      |Self  |
      +------+
          |
          v

     entry_point

      /   |   \
     /    |    \
    A     B     C
```

Каждая слабая ссылка подключается к этому списку.

При уничтожении объекта список обходится и все ссылки получают значение `nullptr`.

---

## Почему используется двусвязное кольцо

Каждый клиент содержит:

```cpp
next
prev
```

Поэтому все ссылки образуют кольцевой список.

Например:

```text
entry_point
     |
     v

A <-> B <-> C
^           |
|           |
+-----------+
```

Такое решение позволяет:

* подключать клиента за O(1);
* отключать клиента за O(1);
* не выделять дополнительную память;
* не хранить внешние контейнеры.

Удаление клиента выглядит как обычное исключение элемента из двусвязного списка.

---

## Два независимых списка

На первый взгляд может показаться, что одного списка достаточно.

Однако система хранит два разных семейства клиентов:

```cpp
TClientPtr<T>
THardClientPtr<T>
```

Для них существуют два независимых списка:

```cpp
entry_point
hard_point
```

и два независимых счётчика:

```cpp
RefCount
HardCount
```

---

## Для чего существует THardPtr

В пользовательском коде обычно используется только:

```cpp
TWeakPtr<T>
```

Объекты прикладной модели редко работают напрямую с `THardPtr`.

Основное назначение `THardPtr` находится внутри RTTI-системы.

Например:

```cpp
TRTTIProduct
```

хранит:

```cpp
THardPtr<TType> pType;
```

а

```cpp
TProduct
```

хранит:

```cpp
THardPtr<IAllocator> Alloc;
THardPtr<IFactory> Factory;
```

Таким образом инфраструктурные объекты RTTI могут удерживать друг друга во время сложных операций регистрации, удаления и перестройки графа типов.

---

## Почему THardPtr не является shared_ptr

Это важный момент.

В стандартной библиотеке сильная ссылка обычно означает владение объектом.

Здесь это не так.

Наличие:

```cpp
THardPtr<T>
```

само по себе не удаляет объект и не управляет временем его жизни.

Система по-прежнему остаётся основанной на явном уничтожении объектов.

Поэтому `THardPtr` лучше воспринимать как специальный служебный канал ссылок RTTI-системы, а не как аналог `std::shared_ptr`.

---

## Перемещение объекта

Одной из самых необычных особенностей системы является корректная работа перемещения.

Предположим существует объект:

```cpp
A
```

и несколько ссылок:

```cpp
ptr1 -> A
ptr2 -> A
ptr3 -> A
```

После перемещения:

```cpp
B = std::move(A);
```

не происходит массового поиска ссылок.

Вместо этого сервер ссылок переносит клиентов на новый объект.

Схематично:

```text
до:

ptr1
ptr2 ---> A
ptr3

после:

ptr1
ptr2 ---> B
ptr3
```

Все ссылки автоматически продолжают работать.

Для пользователя перемещение выглядит прозрачным.

---

## Почему это особенно полезно для std::vector

Большинство контейнеров STL активно перемещают объекты.

Например:

```cpp
std::vector<t_node>
```

может перераспределить память при увеличении размера.

При обычных указателях это приводит к инвалидированию адресов объектов.

В данной системе ссылки переживают такие операции благодаря механизму переноса клиентов между серверами ссылок.

Именно поэтому объекты вроде:

```cpp
t_node
t_text
t_layer_with_offset
```

могут безопасно храниться внутри обычных `vector`.

# Почему система появилась

На момент создания системы меня интересовала не столько защита от удаления объектов, сколько возможность работать с большими графами данных.

Хотелось иметь обычные структуры:

```cpp
struct t_node
{
  ...
};

struct t_link
{
  ...
};
```

обычные контейнеры:

```cpp
std::vector<t_node>
std::vector<t_link>
```

и обычную сериализацию.

Без обязательного наследования от базового класса.

Без отдельного менеджера объектов.

Без ручного ведения таблиц идентификаторов.

---

В какой-то момент появилась идея встроить в объект собственный сервер ссылок.

Так появились:

```cpp
TSelfPtr<T>
TWeakPtr<T>
```

Система позволяла хранить ссылки между объектами и автоматически инвалидировать их после удаления.

Кроме того, ссылки переживали перемещение объектов внутри контейнеров.

На тот момент это выглядело очень привлекательным решением.

---

# Неожиданная проблема

Через некоторое время стало понятно, что проблема ссылок имеет ещё одну сторону.

Рассмотрим структуру:

```cpp
struct t_link
{
  TWeakPtr<t_node> from;
  TWeakPtr<t_node> to;
};
```

Пока все объекты находятся внутри одного процесса, всё работает хорошо.

Но как только возникает необходимость:

* сохранить состояние на диск;
* отправить данные по сети;
* передать данные другому процессу;

оказывается, что указатели не являются данными.

Они являются адресами.

Адрес объекта имеет смысл только внутри текущего процесса.

После загрузки файла или получения сетевого пакета адреса становятся бесполезными.

---

# Ссылки против данных

С точки зрения сериализации существуют два принципиально разных подхода.

Первый подход:

```cpp
TWeakPtr<t_node>
```

Второй подход:

```cpp
int node_id;
```

или

```cpp
string node_name;
```

или любой другой сериализуемый идентификатор.

Во втором случае структура полностью описывается данными.

Её можно:

* сохранить;
* передать;
* восстановить.

Никаких скрытых зависимостей от адресного пространства процесса не возникает.

---

# Постепенный отказ от глобальных ссылок

После накопления опыта оказалось, что многие задачи проще решать без глобальных ссылок между объектами.

Вместо:

```cpp
t_link
  -> t_node
```

удобнее хранить:

```cpp
t_link
  -> node_id
```

а поиск выполнять явно.

Такой подход оказался лучше совместим с:

* сериализацией;
* сетевым обменом;
* сохранением состояния;
* миграцией данных между версиями программы.

Поэтому в новых проектах использование следящих указателей постепенно уменьшалось.

---

# Что осталось полезным

Несмотря на это, сама технология автоматического отслеживания объектов не потеряла ценности.

Она оказалась полезной в инфраструктурном коде.

Например:

* внутри RTTI-системы;
* внутри редакторов;
* внутри инструментов разработки;
* внутри временных графов объектов.

То есть там, где объекты живут в пределах одного процесса и не обязаны покидать его адресное пространство.

---

# Важное наблюдение

За годы работы моё отношение к глобальным ссылкам несколько раз менялось.

Сначала они казались универсальным решением.

Потом казались источником лишних проблем.

Сейчас я скорее рассматриваю их как специализированный инструмент.

Если данные должны свободно сериализоваться и путешествовать по сети, лучше хранить идентификаторы и явные связи.

Если же требуется удобная навигация внутри живого графа объектов одного процесса, следящие ссылки могут существенно упростить код.

Поэтому эта система не претендует на роль универсального решения для всех программ.

Она решает вполне конкретную задачу: безопасную работу со ссылками между живыми объектами без риска получить висячий указатель.
